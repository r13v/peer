# Доски в peer

Предложение: добавить в peer доски, общие для людей и агентов. На доске есть ноды, связи между ними, фреймы и комментарии. Человек работает в браузере, агент — через CLI. Хранится доска каталогом файлов.

## Сценарий

Человек и агенты вместе думают над задачей и сохраняют результат на доске.

- Человек рисует схему: ноды, связи, фреймы. Он двигает, переименовывает и комментирует то, что добавили агенты.
- Агент раскладывает исследование по фреймам. Например, один фрейм — один эксперимент: цели, графики и скриншоты, выводы. Агент вставляет картинки, отвечает на комментарии и правит схему по просьбе человека.
- Доска служит агенту структурированной памятью, которую человек может видеть и править.
- Фреймы упорядочены, поэтому доску можно показать как набор слайдов.

Свободного рисования нет. Все объекты доски — ноды, связи, фреймы и треды комментариев.

Агент работает только со смыслом доски: ноды, их текст, связи, принадлежность к фреймам, треды. Геометрией — координатами, размерами, порядком слоёв — занимается браузер.

## Хранение

Доска — это каталог `<name>.board/`:

```
<name>.board/
  board.json             всё состояние доски
  assets/<sha256>.<ext>  картинки, имя файла — хеш его содержимого
  .lock                  файл блокировки, не меняется и не попадает в git
```

По умолчанию доски лежат в store текущего checkout: `$PEER_HOME/repos/<repo>-<hash>/boards/`, рядом с комнатами. Если пользователь хочет держать доску в репозитории, он указывает путь при создании, например `docs/arch.board`. Формат в обоих случаях один.

Все ссылки внутри доски относительные: `board.json` ссылается на картинки как `assets/<sha256>.<ext>`. Поэтому доску можно перенести или склонировать вместе с репозиторием в другое место, и работа с ней продолжится.

Каждое изменение перезаписывает `board.json` целиком: новая версия пишется во временный файл, который затем переименовывается поверх старого. Всё это происходит под эксклюзивным `flock` на `.lock`. Блокировку держат на отдельном файле, а не на `board.json`: переименование подменяет файл, и блокировка на старом файле ничего бы не защищала. В итоге файл никогда не бывает полузаписанным, а изменения сервера и CLI не теряются.

Сериализация детерминирована: одно и то же состояние всегда даёт одни и те же байты. Ключи объектов идут в фиксированном порядке, порядок массивов сохраняется. Поэтому диффы в git остаются чистыми.

`board.json` можно менять и вне peer: git checkout, мерж, ручная правка. Поэтому схема и инварианты проверяются при каждом чтении. Если файл их нарушает, команда возвращает ошибку с перечнем нарушений и ничего не записывает.

Внешние правки допустимы, только когда с доской никто не работает. После такой правки агент перед продолжением делает новый `inspect`. Защиты от внешней правки, сделанной параллельно с работой в peer, нет: `base` и `expect` сравнивают только номера ревизий. Сервер лишь помогает открытой вкладке: если содержимое файла изменилось, а `revision` не выросла, вкладка перечитывает доску и сбрасывает историю undo.

## Модель

```json
{
  "formatVersion": 1,
  "id": "b_7Qm2",
  "title": "Sandbox research",
  "roomId": "sandbox-cow",
  "revision": 57,
  "nodes": [
    {"id": "f1", "type": "frame", "rev": 12, "title": "Experiment 4: shared CoW",
     "order": 1, "preset": "slide", "x": 0, "y": 0, "w": 1600, "h": 900, "z": 0},
    {"id": "n1", "type": "card", "rev": 54, "parentId": "f1",
     "text": "Warm template\nfull agent image", "color": "green",
     "x": 40, "y": 80, "w": 240, "h": 72, "z": 1},
    {"id": "n2", "type": "image", "rev": 31, "parentId": "f1",
     "asset": "assets/3fa94c…e1.png", "caption": "RSS per VM",
     "x": 360, "y": 80, "w": 640, "h": 400, "z": 2},
    {"id": "n5", "type": "card", "rev": 57, "parentId": "f1", "text": "Cold start"}
  ],
  "edges": [
    {"id": "e1", "rev": 31, "from": "n1", "to": "n2", "label": "measured by"}
  ],
  "threads": [
    {"id": "t1", "rev": 57, "target": {"kind": "node", "id": "n2"},
     "resolved": false, "orphaned": false, "targetLabel": "RSS per VM",
     "messages": [
       {"id": "m1", "author": {"role": "user"}, "body": "Почему разброс у VM 3?",
        "createdAt": "2026-10-10T12:00:00Z"},
       {"id": "m2", "author": {"role": "reader", "roomId": "sandbox-cow"},
        "body": "Холодный старт, см. n5.", "createdAt": "2026-10-10T12:03:00Z"}
     ]}
  ],
  "deleted": [{"id": "e7", "rev": 40}],
  "nextId": 12
}
```

### Ноды

Поля нод делятся на смысловые и геометрические.

| type | Смысловые поля | Смысл |
|---|---|---|
| `card` | `text`, `color?` | Блок с текстом. Текст только plain, абзацы разделяются `\n`. |
| `image` | `asset`, `caption?` | Картинка из `assets/`. |
| `frame` | `title`, `order` | Контейнер для других нод. `order` задаёт порядок фреймов в режиме показа. |

У всех нод есть ещё `id`, `type`, `rev` и необязательный `parentId` — фрейм, в котором лежит нода. Фрейм может лежать внутри другого фрейма.

Геометрические поля: `x`, `y`, `w`, `h`, `z`, а у фрейма ещё `preset`.
- Координаты задаются в единицах доски. У нод с `parentId` они отсчитываются от левого верхнего угла фрейма.
- `z` задаёт порядок отрисовки, порядок массива на него не влияет. Фрейм всегда рисуется под своими детьми.
- `preset: "slide"` фиксирует у фрейма пропорции 16:9.
- Нода без `x` и `y` ещё не размещена — так выглядит нода, которую добавил агент. Она полноценная во всём, кроме положения на экране: её можно читать, связывать и комментировать. Разместит её браузер.

`rev` — номер ревизии доски, на которой нода менялась в последний раз. Так же устроен `rev` у связей и тредов.

### Связи

Поля связи: `id`, `rev`, `from`, `to`, `label?`. Связь соединяет любые две ноды, в том числе ноды из разных фреймов. Маршрут линии нигде не хранится, его строит браузер.

### Треды

Тред — это обсуждение, прикреплённое к объекту. Объектом может быть доска (`{"kind": "board"}`), фрейм, нода или связь.

- У каждого сообщения есть автор. Человек записывается как `{"role": "user"}`, агент — своей ролью в peer и комнатой: `{"role": "reader", "roomId": "..."}`.
- `resolved` закрывает тред, но не удаляет его.
- Если объект удалили, тред остаётся. Ему ставится `orphaned: true`, а в `targetLabel` сохраняется последняя подпись объекта.

### Удалённые объекты

В `deleted` хранятся id удалённых нод, связей и тредов вместе с ревизией удаления. По этим записям `restore` проверяет, что объект с тех пор никто не восстановил и не удалил снова.

### Связь с комнатой

`roomId` у доски необязателен. Он показывает, в какой комнате доску создали. Доска живёт независимо от комнаты: когда комната закончилась, доску можно править дальше.

### Инварианты

- id выдаются из счётчика `nextId`. Новый объект никогда не получает id, который уже был выдан, даже если прежний объект удалён. Под прежним id может вернуться только тот же объект, через `restore`.
- Цепочка `parentId` должна указывать на существующий фрейм и не образовывать цикл.
- `from`, `to` и `asset` должны ссылаться на существующие объекты. Направленные циклы из связей допустимы.
- `x` и `y` у ноды либо есть оба, либо нет ни одного.
- Каждая успешная пачка увеличивает `revision` доски на 1. Каждая изменённая ею сущность, включая изменённые неявно, получает `rev`, равный новой `revision`.

## Операции

Любое изменение доски, кем бы оно ни было сделано, — это пачка операций. Пачка применяется целиком или не применяется вовсе.

```json
{"base": 57,
 "ops": [
   {"op": "add", "ref": "$card", "node": {"type": "card", "parentId": "f1", "text": "Page cache"}},
   {"op": "add", "edge": {"from": "$card", "to": "n2", "label": "explains"}},
   {"op": "update", "id": "n1", "set": {"text": "Warm template"}},
   {"op": "delete", "id": "e1"},
   {"op": "comment", "target": {"kind": "node", "id": "n2"}, "body": "Добавил объяснение"},
   {"op": "reply", "thread": "t1", "body": "Холодный старт, см. n5."},
   {"op": "resolve", "thread": "t1", "resolved": true}
 ]}
```

- **`base`** — ревизия доски, на которой автор видел данные. Её даёт `inspect` или предыдущий `apply`. Вместо `base` пачка может передать `expect` — карту `{id: rev}` с точными ожидаемыми ревизиями затронутых сущностей. Ею пользуется undo во вкладке.
- **`add`** создаёт ноду или связь. `ref` — временное имя вида `$...`. По нему другие операции той же пачки ссылаются на новый объект. В ответе приходит соответствие `ref` → настоящий `id`.
- **`update`** меняет только поля, перечисленные в `set`. Остальные поля, смысловые и геометрические, сохраняются.
- **`delete`** удаляет объект.
  - Вместе с нодой удаляются её связи.
  - Фрейм по умолчанию разгруппировывается. Его непосредственные дети переходят к родителю фрейма: к внешнему фрейму или на доску. Координаты пересчитываются так, чтобы дети остались на тех же местах. С `cascade: true` фрейм удаляется вместе со всем содержимым.
  - Треды удалённых объектов получают `orphaned: true`.
- **`restore`** возвращает удалённый объект под его прежним `id`. Операция несёт полный снимок объекта, проверяет его запись в `deleted`, убирает эту запись и снимает `orphaned` с тредов объекта. Эту операцию отправляет undo во вкладке.
- **`comment`** создаёт тред, **`reply`** добавляет в него сообщение, **`resolve`** закрывает или открывает тред.

Несколько операций одной пачки могут менять одну и ту же сущность. Они применяются по порядку, а сущность получает один новый `rev`.

### Кто что может менять

Пачки CLI и пачки браузера проходят через одну и ту же логику применения. Различаются только допустимые поля:
- CLI-пачка не может задавать и менять геометрические поля, ни в `add`, ни в `update`. `restore` из CLI запрещён. Такие пачки отклоняются с ошибкой.
- Запрет касается только входа CLI. Геометрию по-прежнему меняет сама логика применения:
  - при разгруппировке фрейма размещённые дети сохраняют своё положение на доске, а неразмещённые остаются без координат;
  - если агент меняет ноде `parentId`, координаты ноды сбрасываются, и браузер размещает её заново уже в новом фрейме.
- Пачка браузера может менять любые поля.

`peer board schema` описывает оба варианта.

### Автор

Автор пачки задаётся только флагами CLI, в JSON пачки его нет. Агент указывает `--as ROLE --room ID`, как в остальных командах peer. Без комнаты допустим только `--as user`, он означает человека. Правки из браузера всегда записываются с автором `user`.

### Конфликты

Пачка с `base` отклоняется, если хотя бы одна затронутая ею сущность изменилась после `base`, то есть её `rev` больше `base`. Пачка с `expect` отклоняется, если `rev` хотя бы одной затронутой сущности не равен ожидаемому или если затронутой сущности нет в `expect`. Для удалённого объекта ожидаемым считается `rev` его записи в `deleted`.

Затронутыми считаются сущности, которые пачка меняет явно, и сущности, которые она меняет неявно:
- связи и треды удаляемой ноды;
- дети разгруппировываемого фрейма.

Фрейм, в который добавляют ноду, не затронут: проверяется только то, что он существует. Поэтому две ноды, которые разные авторы добавили в один фрейм, не конфликтуют.

```json
{"error": "conflict", "base": 57, "conflicts": [{"id": "n1", "rev": 59}]}
```

Правки разных сущностей не конфликтуют: пока человек двигает одни ноды, агент может спокойно менять другие. `rev` у ноды один на смысловые и геометрические поля. Поэтому агент может получить конфликт и тогда, когда браузер только разместил или измерил ноду. Получив конфликт, агент перечитывает затронутые сущности через `inspect --ids` и повторяет пачку с новой `base`. Если агент собирает пачку из нескольких чтений, `base` — наименьшая из их ревизий.

### Undo

Undo есть только в браузере, история хранится в памяти вкладки.
- Каждая пачка, отправленная вкладкой по действию пользователя, — один шаг undo. Исключение — `reply`: у ответа в треде нет обратной операции, поэтому его отменить нельзя. Отмена `comment` удаляет созданный тред. Служебные записи вкладки — размещение нод и измерение размеров — в историю не попадают.
- Для каждого шага вкладка хранит обратную пачку и `expect`: ревизии затронутых сущностей сразу после этого шага. Их вкладка берёт из ответа `apply`, в котором перечислены изменённые, созданные и удалённые id.
- Undo отправляет обратную пачку с её `expect`. Если кто-то другой изменил те же сущности, undo отклоняется с конфликтом, и вкладка об этом сообщает.
- После каждого своего undo или redo вкладка переписывает в `expect` остальных шагов истории ревизии сущностей, затронутых этим undo или redo, на значения, которые вернул сервер. Поэтому несколько undo подряд над одной нодой проходят, а чужая правка между ними даёт конфликт. Redo устроен так же.
- Пачки других участников, включая CLI-пачки агентов, в историю вкладки не попадают.
- После перезагрузки вкладки история начинается заново.

## CLI для агентов

Агенты работают с доской через CLI. Все команды пишут JSON в stdout. При ошибке в stderr уходит JSON вида `{"error": "...", ...}`, и команда завершается с ненулевым кодом.

`BOARD` — это имя доски в store текущего checkout либо путь к каталогу `*.board`.

```
peer board create NAME [--title T] [--path DIR] --as ROLE [--room ID]
peer board list
peer board inspect BOARD [--overview | --frame ID | --ids ID,...] [--as ROLE --room ID]
peer board apply BOARD --as ROLE [--room ID]        < ops.json
peer board import-image BOARD FILE [--frame ID] [--caption T] --as ROLE [--room ID]
peer board schema
```

- **`create`** создаёт пустую доску. С `--path` доска создаётся по указанному пути, например в репозитории, а не в store. `--room` записывается в `roomId` доски.
- **`list`** показывает доски текущего checkout: из store, из комнат этого checkout и найденные в текущем каталоге. Для каждой выводятся `id`, имя, путь, `url`, `title`, комнаты, `revision`, а если доска недоступна — ошибка.
- **`inspect`** — основной способ чтения. Он показывает только смысл доски, без геометрических полей. Агенту рекомендуется сначала смотреть `--overview`, потом нужный `--frame`.
  - `--overview` даёт фреймы по `order`: заголовок, число нод, открытые треды. Ноды вне фреймов показываются кратко.
  - `--frame ID` даёт всё содержимое фрейма: ноды, связи с ними и треды.
  - `--ids` возвращает указанные сущности.
  - Без флагов возвращается вся доска.
  - Каждый ответ содержит `id`, `title`, путь и `url` доски, а также `revision` — она служит `base` для следующего `apply`.
  - У картинок вместо относительного пути указан абсолютный. Его `inspect` вычисляет от того места, где доска лежит сейчас. Агент читает картинку по этому пути сам.
- **`apply`** читает пачку из stdin. Ответ: новая `revision`, соответствие `ref` → `id` и списки изменённых, созданных и удалённых id, включая изменённые неявно.
- **`import-image`** копирует файл в `assets/` под именем по хешу содержимого и добавляет ноду `image`. Повторный импорт того же файла не создаёт второй копии. Команда читает и пишет доску под одной блокировкой, поэтому `base` ей не нужна.
- **`schema`** выводит JSON Schema для `board.json`, а также для пачек CLI и браузера.

Все команды работают без запущенного TUI: CLI пишет `board.json` напрямую, под той же блокировкой `.lock`.

Ссылку на доску по известному пути выдаёт любая команда, например `peer board inspect ~/work/x.board --overview`.

## Сервер и веб-интерфейс

Когда пользователь запускает TUI (`peer` без аргументов), вместе с ним стартует HTTP-сервер.

- **Адрес фиксированный:** `http://127.0.0.1:4747`. Порт меняется переменной `PEER_PORT`. Если порт занят чужой программой, TUI показывает ошибку с подсказкой про `PEER_PORT`.
- **Ссылки на доски** выводят `create`, `list` и `inspect`. Без запущенного peer ссылка не откроется, поэтому рядом со ссылкой агент и мод подсказывают запустить `peer`.
- **Один сервер на `PEER_HOME`.**
  - Сервер поднимает тот TUI, который смог взять блокировку `$PEER_HOME/server.lock`. Остальные TUI проверяют `GET /api/health` и пользуются уже работающим сервером.
  - Если на порту отвечает peer с другим `PEER_HOME` или с другим портом в настройках, TUI сообщает о несовпадении и не использует этот сервер.
  - Когда TUI-владелец закрывается, сервер останавливается. Один из оставшихся TUI берёт блокировку и поднимает сервер на том же порту, а открытые вкладки переподключаются сами.
- **Несколько досок одновременно.** Один сервер обслуживает все доски. У каждой доски своя блокировка, поэтому агенты из разных комнат и сессий, работающие с разными досками, друг другу не мешают.
- **Адресация досок.** В URL доски стоит ключ — абсолютный путь её каталога в кодировке base64url, а не `id` из `board.json`. Сервер открывает доску по ключу напрямую, заранее знать о ней ему не нужно. Если по пути нет каталога `*.board` с корректным `board.json`, сервер отвечает ошибкой. Сам `GET` по ссылке ничего не записывает. Открытая вкладка затем может отправить служебные пачки: размещение и измерение нод. Копия доски по другому пути — это другая доска с другой ссылкой, хотя `id` у них совпадает. Если каталог доски перенести, старая ссылка перестаёт работать, новую выдают `list` и `inspect`.
- **SPA** — React и `@xyflow/react` (MIT). Сборка встроена в бинарник через `go:embed`. Доска рисуется целиком только в браузере.
- **API** (`{key}` — ключ доски):
  - `GET /api/health` — проверка, что сервер жив, с `PEER_HOME` и портом;
  - `GET /api/boards` — список досок для главной страницы;
  - `POST /api/workspaces` — TUI сообщает серверу свой рабочий каталог;
  - `GET /api/boards/{key}` — полный снимок доски, вместе с геометрией;
  - `POST /api/boards/{key}/apply` — пачка операций;
  - `POST /api/boards/{key}/assets` — загрузка картинки;
  - `GET /api/boards/{key}/events` — SSE;
  - `GET /b/{key}/assets/...` — файлы картинок.
- **Чтение и запись.** Сервер пишет тот же файл под той же блокировкой, что и CLI, своей логики записи у него нет. Раз в 500 мс сервер проверяет `board.json` на изменения и при изменении рассылает по SSE событие с новой `revision`. Вкладка, получив событие или переподключившись, перечитывает снимок доски.

### Список досок и история

Отдельного реестра досок нет. Список собирается из того, что уже есть в peer.

**Доски комнаты.** Данные комнаты в store хранят поле `boards` — абсолютные пути досок, с которыми в ней работали. Любая команда `peer board ... --room ID` добавляет туда путь доски:
- до работы с доской команда проверяет, что комната активна и `--as` — её участник; иначе команда отклоняется и доску не трогает;
- путь добавляется только после успешной операции над доской, под той же блокировкой store, что и остальные изменения комнаты; блокировки доски и store никогда не держатся одновременно;
- если записать путь в комнату не удалось, операция над доской всё равно считается успешной: ответ содержит её результат и предупреждение `roomLink`, а путь добавится при следующей команде с этой доской и этой комнатой.

Связь комнат и досок — многие ко многим: в одной комнате можно работать с несколькими досками, одна доска может встречаться в нескольких комнатах. История комнат, включая завершённые, уже есть в peer, поэтому доски завершённой комнаты остаются доступны из её карточки.

**Рабочие каталоги.** Каждый запущенный TUI сообщает серверу свой рабочий каталог через `POST /api/workspaces`. После смены владельца сервера все живые TUI регистрируются заново. Поэтому закрытие одного TUI не меняет набор найденных досок у остальных.

**Поиск `*.board`.**
- В рабочем каталоге из git-репозитория поиск идёт по отслеживаемым и неигнорируемым файлам git, без лимита глубины. Он ограничен самим рабочим каталогом: если peer запущен в подкаталоге репозитория, весь репозиторий не сканируется.
- Вне git каталог обходится на глубину до 4 уровней. Скрытые каталоги, `node_modules`, `vendor` и символические ссылки пропускаются. Главная страница сообщает об этой границе рядом с полем «Открыть по пути».
- Внутрь найденного `*.board` поиск не спускается.
- Сканирование запускается при регистрации рабочего каталога и по кнопке «Обновить», но не при каждом открытии главной страницы. Результат хранится в памяти сервера.

**Главная страница** `http://127.0.0.1:4747/` группирует доски по checkout, как TUI группирует комнаты. Внутри группы три раздела:
1. **Комнаты** — активные и из истории, с их досками. Одна доска может стоять у нескольких комнат.
2. **В store** — доски из `$PEER_HOME/repos/<checkout>/boards/`, отсортированные по времени изменения `board.json`.
3. **Найдены в рабочем каталоге** — результат поиска.

У каждой связанной комнаты доска показывается в её карточке. В разделах «В store» и «Найдены» доска не повторяется, если она уже видна у какой-то комнаты, и не повторяется между этими двумя разделами. Если по пути из комнаты доски больше нет или её `board.json` не проходит проверку, карточка показывает это вместо ссылки. Поиск идёт по названию, имени каталога и пути.

**Открыть по пути.** На главной странице есть поле для абсолютного пути. Оно просто ведёт на ссылку этой доски. Отдельно запоминать такую доску не нужно: её ссылка работает и после перезапуска. Если с доской работали в комнате, она будет видна у этой комнаты.

**TUI.** В карточке комнаты TUI показывает её доски и их ссылки.

### Размещение и размеры

- Открытая вкладка сама размещает неразмещённые ноды: послойно по связям, внутри их фрейма, через ELK или dagre в браузере. Уже размещённые ноды она не двигает и обходит как препятствия. Если неразмещён сам фрейм, сначала размещаются фреймы, потом их содержимое. Позиции она сохраняет одной служебной пачкой с `base` того снимка, по которому считала раскладку. Пачка размещает все неразмещённые ноды сразу, частичное размещение не отправляется.
- Если две вкладки разместили одни и те же ноды, вторая получает конфликт. Она перечитывает доску и размещает только то, что всё ещё не размещено. Старые позиции она не повторяет.
- Размеры нод вкладка измеряет после отрисовки и записывает, только если они отличаются от сохранённых. Размеры считаются по единым правилам: в единицах доски, независимо от масштаба, со шрифтами из сборки SPA и фиксированным округлением. Поэтому разные вкладки получают одинаковые размеры и не перезаписывают друг друга.
- Ручное перемещение просто сохраняет новые координаты. Кнопка «Упорядочить» заново раскладывает выбранный фрейм. Это действие пользователя, и оно попадает в undo.

### Что умеет SPA

- создавать карточки и фреймы, удалять любые объекты;
- двигать и менять размер нод и фреймов;
- создавать связи, перетаскивая линию от одной ноды к другой;
- редактировать текст прямо на карточке;
- перетаскивать картинки на доску;
- раскрашивать карточки;
- видеть треды у объектов и у всей доски, начинать треды и отвечать в них;
- отмечать треды решёнными;
- искать по тексту доски;
- пользоваться мини-картой и undo;
- упорядочивать фрейм;
- показывать фреймы как слайды по `order`.

Изменение сохраняется, когда действие закончено: перетаскивание отпущено, редактор текста закрыт.

## Claude Code Mods

Мод показывает в Claude Code упрощённое превью доски и ссылку на неё. Путь и `url` доски мод берёт из `peer board list`, а `board.json` читает сам, вместе с геометрией.
- На desktop превью — элемент `Svg` с прямоугольниками фреймов и нод, линиями связей и подписями. Неразмещённые ноды показываются списком под схемой. Если доска не помещается в лимит размера `Svg`, мод рисует только фреймы.
- В терминале превью — список фреймов с числом нод и открытых тредов.
- `Link` открывает доску в браузере. Рядом подсказка: если ссылка не открывается, запустите `peer`.

Превью нужно, чтобы быстро понять, что на доске. Точную картинку показывает только браузер.

## Безопасность

- Сервер слушает только `127.0.0.1`. Модель угроз — чужие сайты в браузере пользователя. Локальные процессы того же пользователя и так могут читать файлы досок.
- Канонический адрес один: `http://127.0.0.1:PORT`. Все ссылки ведут на него. Запросы с другим заголовком `Host` отклоняются: это защита от DNS rebinding.
- Все `POST`-запросы — `apply`, загрузка картинок, регистрация рабочего каталога — требуют заголовок `X-Peer` и `Origin`, равный `http://127.0.0.1:PORT`. TUI, обращаясь к серверу, передаёт их так же. Пустой и `null` Origin отклоняются. Из-за нестандартного заголовка чужой сайт не может отправить такой запрос без preflight, а CORS-заголовков сервер не отдаёт.
- SPA нельзя встроить в чужую страницу: `Content-Security-Policy: frame-ancestors 'none'` и `X-Frame-Options: DENY`. Иначе чужой сайт мог бы открыть доску во фрейме, и её код отправил бы служебные пачки с `Origin` самого peer. Если чужой сайт откроет ссылку на доску в новой вкладке, вкладка может разместить неразмещённые ноды. Это та же запись, что произошла бы при открытии доски самим пользователем, и других изменений она не делает.
- `GET` ничего не меняет. API и SSE отклоняют запросы с чужим `Origin`. Картинки отдаются с `Cross-Origin-Resource-Policy: same-origin`, JSON — с `X-Content-Type-Options: nosniff`.
- Пути к картинкам принимаются только в виде `assets/<sha256>.<ext>`. Файл должен лежать внутри каталога доски и не быть символической ссылкой.
- Тип картинки определяется по содержимому файла, а не по расширению. Разрешены png, jpeg, gif, webp. Размер файла ограничен, по умолчанию 20 МБ.
- `board.json` проходит проверку схемы и инвариантов при каждом чтении и каждой записи. Пачка, которая нарушает инвариант, отклоняется целиком.
- Данные с доски — это данные, а не инструкции. Skill для агентов говорит об этом прямо, как уже делает для сообщений комнат.

## Версии формата

`formatVersion` — целое число. Доску с версией новее, чем знает peer, нельзя ни читать, ни писать: команда объясняет, что нужно обновить peer. Если когда-то выйдет новая версия формата, peer будет переводить старую доску на неё при первой записи, под блокировкой и с резервной копией `board.json.v<N>`.

## Границы первой версии

В первую версию не входят:
- удаление неиспользуемых файлов из `assets/`;
- журнал изменений: на вопрос «что изменилось с ревизии N» первая версия не отвечает;
- undo для CLI и undo, который переживает перезагрузку вкладки;
- текст с форматированием в нодах;
- экспорт доски в картинку или PDF;
- доступ к доске с другой машины.

## Критерии приёмки

1. Агент и человек одновременно правят разные ноды. Обе правки сохраняются, и вкладка показывает правку агента без перезагрузки.
2. Агент и человек одновременно правят одну и ту же ноду. Вторая правка получает `conflict`, первая сохраняется.
3. Два undo подряд над одной нодой во вкладке проходят. Если между ними ноду изменил агент, второй undo получает `conflict`.
4. Удаление ноды удаляет её связи, а её треды становятся `orphaned`. Undo во вкладке возвращает ноду и связи с прежними `id`, а треды перестают быть `orphaned`.
5. Удаление фрейма без `cascade` оставляет детей на тех же местах на доске. Дети вложенного фрейма переходят во внешний фрейм.
6. Пачка с ошибкой в одной операции не меняет доску вообще.
7. CLI-пачка с геометрическим полем или с `restore` отклоняется. Та же пачка из браузера принимается.
8. `inspect` не содержит геометрических полей.
9. Агент без запущенного TUI создаёт доску, добавляет ноды, связи, картинки и комментарии. При первом открытии в браузере все ноды размещаются автоматически, и это размещение не попадает в undo.
10. Агент переносит ноду в другой фрейм. Браузер размещает её внутри нового фрейма, не сдвигая остальные ноды.
11. Две вкладки одновременно размещают одни и те же неразмещённые ноды. Сохраняется одно размещение, вторая вкладка перечитывает доску и ничего не перезаписывает.
12. `import-image` того же файла дважды создаёт один файл в `assets/`. Доска после закрытия и повторного открытия выглядит так же, все картинки на месте.
13. Каталог доски перенесён в другое место. `inspect` отдаёт новые абсолютные пути к картинкам, `list` — новую ссылку, картинки открываются.
14. Если запустить peer в склонированном репозитории, его доски появляются на главной странице в разделе «Найдены в рабочем каталоге» и открываются.
15. Чтение доски и повторная запись того же состояния без пачки не меняют `board.json` побайтово.
16. Две комнаты из разных checkout одновременно работают с двумя разными досками. Ни одна правка не теряется.
17. Два TUI запущены в разных каталогах. Главная показывает доски из обоих каталогов, и после закрытия TUI-владельца ничего не пропадает.
18. Доска завершённой комнаты открывается из карточки этой комнаты.
19. Если каталог доски из комнаты удалили, карточка комнаты сообщает, что доски нет.
20. Ссылка на доску, которую выдал CLI без запущенного TUI, открывается после запуска `peer`. Ссылка на путь без корректной доски даёт ошибку, и ничего не записывается.
21. Сервер слушает только `127.0.0.1:PEER_PORT`. Он отклоняет запросы с чужим `Host`, запись без `X-Peer` или с чужим `Origin`. SSE работает из своей вкладки.
22. Если закрыть TUI, который поднял сервер, сервер поднимает другой запущенный TUI на том же порту, и открытая вкладка продолжает работать.
23. Если поменять `board.json` вне peer при открытой вкладке, вкладка перечитывает доску и сбрасывает историю undo.
