# Плагин peer для Codex

Статус: реализовано на ветке `codex-plugin` (комнаты `codex-plugin`, `codex-plugin-delivery`, `codex-plugin-impl`).

Проверено на живом Codex 0.160.1 во временном `CODEX_HOME` (2026-10-06):
- `codex plugin marketplace add <repo>` берёт `.agents/plugins/marketplace.json` (`r13v-codex`), а не `.claude-plugin`; `codex plugin add peer@r13v-codex` ставит плагин, хуки видны в `/hooks` и требуют доверия.
- `session_id` хука совпадает с UUID rollout-файла; PostToolUse получает настоящий вывод Bash; `forward`, запущенный хуком с `Setsid`, переживает хук.
- Сообщение участника будит простаивающую сессию: Codex начинает ход без Enter. `peer wait --as main` при живом `forward` отклоняется.
- `/exit` только отключает от сессии («Any running work continues»), SessionEnd не вызывается. `codex resume` вызывает SessionEnd, и хук SessionEnd останавливал `forward` через 1 с после resume (воспроизведено дважды). Поэтому SessionEnd убран; повторный прогон start → /exit → resume → доставка → `peer end` прошёл: заметка о конце пришла, `.done` записан, `forward` вышел.

## Зачем

В Claude Code main не тратит ход на `peer wait`: плагин читает комнату за него и сам начинает ход с новыми сообщениями. В Codex сейчас main и участники держат `peer wait` сами, и каждый раз это отдельный ход модели. Плагин даёт Codex-main ту же доставку без `wait`.

Чего плагин не даст: панели, кнопки 👥 под composer, тостов. Документированного API для своего UI в Codex CLI/IDE не нашли. В TUI `tui.status_line` и `tui.terminal_title` принимают только встроенные поля. Комнату смотрят в `peer` TUI или в плагине Claude.

## Совместимость: без плагина всё по-старому

Тем, у кого нет плагина, будь то Codex, Claude без плагина, pi или любой агент со standalone-skill `skills/peer`, ничего не меняется:

- `skills/peer` и тексты `peer skills flow|main|member|worker` (`instructions/*.md`) не меняются. Исключение «main не делает `peer wait`» есть только в skill `team` самого плагина, как сейчас в плагине Claude.
- `peer forward` — новая команда, только добавляется. Существующие команды и их вывод (`start`, `wait`, `send`, `invite`…) не меняются, `deliverBatch` вызывается как есть.
- Отказ явному `peer wait` при живом `forward` срабатывает только для роли, у которой плагин запустил `forward`. Без плагина `forward` никто не запускает, и `wait` работает как раньше. Отказ решает только реально удерживаемый flock: отсутствующий или устаревший файл привязки `wait` не запрещает, и после падения `forward` `wait` сразу снова доступен.
- В `--help` появляется `forward`, но JSON существующих команд новых обязательных полей не получает.
- `forward` держит общий lock store только на короткие `readBatch` и `commitBatch` (обычный `wait` держит его ещё и пока пишет в stdout). Во время `queue` lock свободен, так что другие комнаты и пользователи без плагина его не ждут.
- `peer invite … --agent codex` по-прежнему запускает `codex exec --json`, и участник делает свой `wait`.
- Тест: существующие тесты `main_test.go` проходят без изменений. Сценарий start → invite → wait → end без `forward` даёт тот же вывод. После остановки или падения `forward` прежний `wait` той же роли снова работает.

## Почему так: `codex queue`

Хуки Codex не умеют начать ход сами: async-хук ждёт следующего хода пользователя, Stop-хук продлевает только текущий ход. Свой клиент app-server (`turn/start`) — отдельный продукт.

В codex-cli 0.160.1 есть `codex queue --thread UUID --message TEXT`, но в документации его нет. Проверка на одноразовых сессиях в tmux 2026-10-06:

| Проверка | Итог |
|---|---|
| `--thread` по имени после `/rename` | ошибка «Cannot verify a unique session label», нужен UUID |
| Сессия простаивает | ход начался сам, без Enter; сообщение видно обычной строкой пользователя |
| Сессия занята (`sleep 20`), два сообщения | `sleep` не прерван; оба пришли после конца хода, каждое отдельным ходом, по порядку, без дублей |
| После `/exit` | ход всё равно прошёл без окна, ответ есть в журнале сессии |
| `codex --no-daemon` | доставка тоже работает |

UUID — суффикс файла `~/.codex/sessions/YYYY/MM/DD/rollout-…-<UUID>.jsonl`.

## Дизайн

### 1. `peer forward ID --as main --codex-thread UUID` (Go)

Единственный читатель комнаты за main. Каждая пачка проходит три шага; `deliverBatch` и обычный `wait` не меняются:

1. **`readBatch`** под общим lock: проверить комнату и роль, прочитать пачку с теми же ограничениями, что у `deliverBatch` (16 сообщений, 32 KiB, oversized, `ended` только после последней пачки; `store.go:744-769`) и смещение `next`. Курсор не двигается.
2. **`codex queue --thread UUID --message TEXT`** без lock, через `exec.CommandContext` с конечным deadline (например 15 с) и убийством процесса по нему. Ошибка — повтор той же пачки с ограниченным backoff. Зависший `queue` не блокирует `send`, `status` и `end` других комнат.
3. **`commitBatch`** под lock: снова проверить комнату и роль и записать `cursor = next`, только если курсор всё ещё равен старому смещению. Если не равен, курсор назад не откатывать: `queue` уже принят, просто перечитать текущий курсор.

Если комната закончилась между шагами 1 и 3, остаток и заметка о конце приходят следующей пачкой.

Почему так, а не `deliverBatch` с `queue` внутри `write`: `write` выполняется под общим lock checkout (`store.go:727`), и тогда каждый `queue` (около секунды, а при зависании — до deadline) задерживал бы все комнаты. Почему обычный `wait` не переводим на эту схему: два `wait` одной роли сейчас делят сообщения под lock, а с разделёнными шагами оба получили бы одну пачку. Это меняет поведение без плагина.

- Одна пачка — один `codex queue`, потому что каждое сообщение из очереди становится отдельным ходом.
- Текст пачки — данные с автором и ролью, а не инструкции, плюс id пачки. Сбой между принятием `queue` и записью курсора даст дубль, поэтому доставка at-least-once. Модель распознаёт повтор по id.
- Блокировка — flock на файл `sessions/<room>/forward-<role>.lock` в store, то есть на checkout, комнату и роль, а не на сессию Codex. Иначе две сессии получили бы разные блокировки и обе стали бы доставлять одну комнату. Живость определяет удерживаемый flock, а не pid: pid может достаться другому процессу. Второй `forward` той же роли выходит с ошибкой.
- Явный `peer wait` той же роли, пока `forward` держит flock, отклоняется. Чтобы не было гонки «`wait` проверил, `forward` взял flock, `wait` сдвинул курсор», `forward` берёт flock под общим lock store, а `wait` проверяет его внутри того же lock до чтения курсора.
- `status: ended`: отправить последние сообщения и явное «комната завершена, задачу не продолжай», затем выйти. `kicked` для main невозможен (`store.go:851`); обрабатываем его только на всякий случай: сообщить и выйти.
- SIGTERM: выйти, не начиная нового `queue`, и убить текущий `queue`.

### Почему `forward` в Go, а не скрипт в плагине

Рассматривали вариант без новой команды: фоновый скрипт плагина читает `peer watch`/`peer log --json`, хранит свою отметку доставки и вызывает `codex queue`, как Claude-плагин (`plugin/hooks/register.tsx:295-401`). Отказались:

- У Codex-пользователя гарантированы только `codex` и `peer`. На `sh` без `jq` JSON не разобрать, а `sh` с `peer wait` теряет пачку при падении между `wait` и `queue`. Node или Python — новая зависимость.
- Без потерь скрипту нужен `ack` до доставленного сообщения, а не до конца комнаты (см. ниже), то есть изменение Go всё равно.
- В Go уже есть курсор по смещению, ограничения пачки по размеру и точный `ended`.

Для Claude-плагина `forward` бесполезен: доставка там идёт через `$.prompt.submit` внутри процесса Claude Code.

### 2. Плагин Codex (`codex-plugin/`)

- `.codex-plugin/plugin.json` + `skills/team`, `skills/say` + `hooks/hooks.json`. Только command-хуки, без MCP. Все хуки запускают скрытую подкоманду `peer codex-hook`: JSON события разбирает Go, а не `sh`. Маркетплейс — `.agents/plugins/marketplace.json` с именем `r13v-codex`.
- Привязка — запись на сессию и комнату: `$PLUGIN_DATA/sessions/<session_id>/<hash(repo)>-<room>.json` с полями repo и room — по файлу на комнату, так что параллельные хуки не перезаписывают друг друга; живость и владелец `forward` — flock и `{pid, thread}` в его lock-файле. Общего файла «текущая сессия» нет: иначе при двух сессиях Codex в одном checkout последняя перезаписала бы UUID, и комната ушла бы чужому агенту. Каждый хук берёт `session_id` из своего stdin.
- **PostToolUse** (Bash): поймать успешный `peer start` (main создаётся только им, `store.go:422`; `peer join … main` запрещён, `store.go:94`) и запустить в фоне `peer forward ID --as main --codex-thread $session_id`. Маркер «доставка через codex queue активна» (`additionalContext`) хук выдаёт только после того, как `forward` взял lock роли и подтвердил старт, например строкой `ready` в stdout. Если запуска не было, маркера нет.
- **SessionStart** при resume: если у этого `session_id` есть привязка к комнате, которая ещё активна или закончилась, но её финальная пачка ещё не доставлена, снова запустить `forward`. Пример: `forward` упал с непрочитанными, main за это время закончил комнату — тогда при resume приходят остаток и заметка о конце. Признак «финальная доставка подтверждена» — файл `sessions/<room>/forward-<role>.done` в store. `forward` пишет его под тем же lock сразу после успешного `commitBatch` пачки `ended`. Если курсор не совпал, файл не пишется, пока `forward` не перечитает курсор. Падение между принятым `queue` и `.done` может повторить заметку: доставка at-least-once, а не exactly-once. Если файл есть, `forward` не запускается и заметка о конце не повторяется при каждом resume. Запуск с тем же UUID и по тому же контракту: маркер «доставка активна» (`additionalContext` SessionStart) выдаётся только после `ready`. Чужие комнаты этого checkout не трогать.
- ~~**SessionEnd**~~: убран после проверки на живом Codex 0.160.1. `/exit` лишь отключает от сессии ("Any running work continues"), а SessionEnd вызывается при `codex resume` — хук останавливал `forward` ровно тогда, когда возобновлённая сессия на него рассчитывала. `forward` живёт до `peer end`.
- Skill `team`: исключение «main не делает `peer wait`» действует только после маркера «доставка активна» от PostToolUse или SessionStart. Без маркера, например если хукам не дали доверие, main работает по обычным инструкциям с `wait`.
- `say` — skill, а не команда: в Codex его выполняет модель. `add` не нужен: в Codex человек и так говорит с main напрямую.
- PreToolUse не используется: `peer wait` при живом `forward` отклоняет сам CLI.

### Гарантии, которые обещаем

- Доставка at-least-once, с id пачки.
- `forward` живёт до `peer end`; плагин его не останавливает ни при `/exit`, ни при SessionEnd (см. результаты живой проверки выше). Закрытая в TUI сессия Codex продолжает выполнять ходы из очереди.
- Откат — остановить `forward` и выключить плагин. Сообщения, уже переданные в `queue`, считаются прочитанными, и ходы из очереди Codex могут выполниться уже после выключения. Это нужно написать в README. Проверка «сессия загружена» не показывает, открыт ли TUI, и гарантией не считается.
- Хуки плагина пользователь одобряет через `/hooks` после установки и после каждого изменения. Хуки на уровне репозитория работают только в доверенном репозитории.

## Порядок работ

1. `peer forward`: блокировка роли, обёртка пачки, `ended`/`kicked`/SIGTERM. Тесты, где `codex` подменён фейковым бинарём в `PATH`:
   - `queue` падает: курсор не сдвинулся;
   - `queue` не выходит никогда: пока он висит, `send` и `end` в другой комнате работают сразу; после deadline курсор прежний;
   - второй `forward` той же роли отклонён и не печатает `ready`;
   - `wait` той же роли при живом `forward` отклонён; после остановки или падения `forward` снова работает;
   - две сессии и две комнаты в одном checkout: каждая пачка уходит своему UUID;
   - комната закончилась между `readBatch` и `commitBatch`: остаток и заметка приходят следующей пачкой;
   - `forward` упал с непрочитанными, комната закончилась, `forward` запущен снова: остаток и заметка приходят один раз, пишется `.done`; следующий запуск сразу выходит и ничего не шлёт;
   - конец комнаты;
   - два обычных `wait` одной роли по-прежнему делят сообщения.
2. Ручная проверка на живом Codex: совпадает ли `session_id` из хука с UUID rollout, срабатывает ли SessionEnd на `/exit`. Итог: совпадает; `/exit` не вызывает SessionEnd, а `codex resume` вызывает — поэтому хук SessionEnd убран.
3. Плагин: хуки, skill, README, установка.
4. Позже: перевести на `queue` участников (`agent.go:85`, сейчас `codex exec --json` и свой `wait`).

## Отдельная задача: `peer ack` для Claude-плагина

Нашли при обсуждении, к Codex-плагину не относится. Claude-плагин сдвигает курсор main циклом до 20 × `peer wait --timeout 0` (`plugin/hooks/register.tsx:382`):

- Курсор уходит в конец комнаты, вместе с сообщениями, которые плагин ещё не доставил (`register.tsx:357-360`). Если плагин после этого упадёт или его выключат, обычный `wait` их не увидит.
- 20 итераций не всегда доходят до конца: пачка — до 16 сообщений, а oversized-сообщение идёт отдельной пачкой (`store.go:757-758`), так что цикл может продвинуться всего на 20 сообщений.

Решение: новая команда `peer ack ID --as ROLE --upto MSG_ID` — курсор до конца сообщения `MSG_ID`, только вперёд. Поиск идёт `scan` от текущего курсора, индекс id → смещение не нужен. Если от курсора id не найден, второй `scan` с начала отличает «уже позади курсора» (успех, ничего не делает) от неизвестного id (ошибка). Плагин вызывает её после каждой доставки с id последнего сообщения пачки. Без плагина ничего не меняется.
